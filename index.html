SAP HANA on Azure

Five checks before moving SAP HANA to Azure

Infrastructure decisions made early decide how smooth a HANA migration will be. These are the five we review first.

1. Certified compute

Run HANA only on virtual machine types and storage configurations listed in SAP’s Certified and Supported SAP HANA Hardware Directory. Size from measured memory use with headroom for working memory and growth — not from the nominal RAM of today’s server.

2. Storage layout

/hana/data and /hana/log have different latency needs. Use the storage combinations Microsoft documents for HANA — such as Premium SSD v2, Ultra Disk or Azure NetApp Files — and verify throughput with SAP’s HANA Hardware and Cloud Measurement Tools before go-live.

3. Latency between tiers

Keep application servers close to the database: same availability zone, accelerated networking and proximity placement groups where needed. Measure round-trip times between application and database instead of assuming them.

4. High availability and disaster recovery

HANA System Replication between zones with a Pacemaker cluster covers local failures; a replica in a second region covers disasters. Agree on RPO and RTO with the business before choosing the topology.

5. Restore drills

Azure Backup for SAP HANA works through the Backint interface; native file backups are another option. Either way, schedule a full restore test — the restore time, not the backup, is what the business feels.

SAP Finance · Power BI

Power BI on SAP Finance data without spreadsheet detours

Finance teams trust numbers that reconcile to the ledger. A few modeling choices make that the default instead of a monthly exercise.

Start from the Universal Journal

In SAP S/4HANA, table ACDOCA holds financial and management accounting line items in one place. Building on it avoids stitching together separate FI and CO extracts.

Extract instead of querying live

Land the data in a governed layer — a lakehouse, a warehouse such as Snowflake, or SAP Datasphere — and refresh it incrementally. Heavy reporting queries should not compete with the transactions running in your ERP.

Model a star schema

Use one fact table for journal lines and shared dimensions for company code, account, cost center, profit center and period. Keep SAP hierarchies, such as financial statement versions, as proper parent–child dimensions.

Secure by row

Row-level security on company code or cost center lets one report serve every controller — without copying files around.

Reconcile automatically

A daily check that totals by company code and period match the trial balance turns trust into a test that either passes or fails.

Snowflake

Where Snowflake credits really go

For most analytics teams, compute rather than storage drives the bill. Four habits keep it predictable.

Know the billing model

A virtual warehouse consumes credits while it runs, billed per second with a 60-second minimum each time it starts or resumes. Many short resumes of a large warehouse add up quickly.

Suspend early, size deliberately

Short auto-suspend periods suit BI and ad-hoc warehouses. Scale up when the query profile shows spilling to remote storage; otherwise a smaller warehouse running slightly longer is often cheaper.

Separate the workloads

Give ELT, BI and data science their own warehouses, and set resource monitors with credit quotas so a runaway job stops before it surprises anyone.

Mind the storage you don’t see

Time Travel and Fail-safe keep history for frequently changing tables. Transient tables or shorter retention suit staging data that can be rebuilt.
